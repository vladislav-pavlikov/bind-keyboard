# bind-keyboard 1.0 Readiness Design

**Goal:** Close the remaining gaps identified for a `1.0.0` release, add a non-blocking "commonly reserved browser/OS shortcut" hint, and ship a public live demo page — then bump `0.1.0` → `1.0.0`.

This covers three independent streams. Each is scoped to touch a distinct part of the repo and can be implemented (and reviewed) as its own group of tasks in one combined plan, following the same pattern as the earlier modernization plan (`docs/superpowers/plans/2026-09-02-modernize-bind-keyboard.md`).

---

## Stream 1: API completeness for 1.0

**Why now, not after:** these are all things that are cheap to fix before 1.0 and become breaking changes (or permanent regret) if fixed after.

1. **Export the `Types` namespace to consumers.** Currently `src/index.ts` only exports `{ BindKeyboard, Classes, helpers }` (plus the default export) — none of `AddBindingOptions`, `KeybindCallback`, `ConstructorProps`, `KeybindInitializer`, `EventType`, `DebugLevel`, `KeyMode`, `KeyCombination`, `KeyCombinationConstruct` can be imported by name from `"bind-keyboard"`. Add `export type * as Types from "./types";` alongside the existing exports, so consumers can write `import type { Types } from "bind-keyboard"` and reference `Types.AddBindingOptions`, etc. (Matches the existing internal naming convention — no new top-level names to design.)

2. **Export `KeybindError` at the top level**, not just as `Classes.KeybindError`. Add it to the named export list: `export { BindKeyboard, Classes, helpers, KeybindError }`. `Classes.KeybindError` keeps working (no removal, purely additive) — this just gives `import { KeybindError } from "bind-keyboard"` as a shorter, more discoverable alternative for the common `catch (e) { if (e instanceof KeybindError) }` pattern. Document it in the README's `.add()`/`.remove()` "throws" notes.

3. **Add `CHANGELOG.md`.** One entry for `0.1.0` (summarizing the breaking changes already shipped: `add()`'s return type, `KeybindEntry`'s constructor shape, `checkInputElements` covering `<select>`/contenteditable) and one for the upcoming `1.0.0` (this stream's additions). Keep it terse — a bullet list per version, not prose.

4. **Resolve the two chord/sequence `// TODO` comments in `src/index.ts`.** They describe unimplemented future features ("g then o" style sequences, "shift+g or o" alternates) that aren't in scope for 1.0. Remove the inline TODOs from the source (a 1.0 release shouldn't ship with unfulfilled promises baked into the code) and instead note them as "not currently supported" in the README's Features section, worded as a known limitation rather than a commitment.

5. **Close test coverage gaps** (current: 98.77% funcs / 98.00% lines via `bun test --coverage`). Specifically uncovered:
   - `src/index.ts:11-25` (`logDebugEvent`) — no test exercises `debug: 1` or `debug: 2`.
   - `src/helpers/getKeyCombination.ts:34-36` — the `KeybindError("Not one key is defined...")` throw branch is never hit.
   - Not covered at all: `.getTarget()`, `BindKeyboard.keyParser`/`BindKeyboard.getKeyCombination` (the static re-exports), the deprecated `startListners`/`stopListners` aliases actually being callable.
     Add one test per gap.

6. **Add an "exports resolve" smoke test to CI.** Verifies both consumption paths actually work post-build: `require("./dist/bind-keyboard.umd.cjs")` (CJS) and `import("./dist/bind-keyboard.js")` (ESM) both resolve and expose a working `BindKeyboard`. This is a real, common class of bug (misconfigured `package.json#exports`) that nothing currently catches automatically. Implementation: a small script (`scripts/check-exports.mjs`, same style as `scripts/check-bundle-size.mjs`) run in CI's `test` stage right after `npm run build`.

7. **Polish:** fix the grammar in `getKeyCombination`'s error message ("Not one key is defined. Enter at least 1 parameter" → something like "At least one key or modifier must be provided.").

## Stream 2: Reserved-shortcut hint (already designed, approved)

Non-blocking, `debug`-gated `console.warn` when `.add()` registers a bare `ctrl+<letter>` or `meta+<letter>` combination that commonly collides with a browser/OS shortcut. New file `src/helpers/getReservedShortcutHint.ts`:

```ts
const RESERVED_KEY_DESCRIPTIONS: Record<string, string> = {
  p: "Print",
  s: "Save",
  f: "Find in page",
  g: "Find next",
  d: "Bookmark this page",
  u: "View page source",
  r: "Reload the page",
  l: "Focus the address bar",
  h: "Browser history",
  j: "Downloads",
  n: "New window",
  t: "New tab",
  w: "Close tab",
  q: "Quit the application",
};
```

Built into a `Map<string, string>` keyed by `"ctrl + <letter>"` and `"meta + <letter>"` (exact match only — combos with an extra `shift`/`alt` held don't match, since those are much less likely to collide). Wired into `add()`'s existing `if (this.#debug) { ... }` block in `src/index.ts`, alongside the existing "overwriting existing binding" warning:

```
[bind-keyboard] "ctrl + p" is commonly used by browsers/OS for "Print". Your callback must call event.preventDefault() for this binding to actually take over — make sure that's intended.
```

Purely informational — the library never auto-`preventDefault()`s or blocks registration. One new test: registering `"ctrl+p"` with `debug: 1` triggers a `console.warn` containing "Print"; registering it with `debug: 0` (default) does not warn at all.

## Stream 3: Public demo page (GitLab Pages)

### Purpose & hosting

Public, deployed demo — linked from the README — showing the library working live. Hosted on **GitLab Pages** (this repo is on GitLab; free, no external service, deploys from a new `pages` CI job on `main`).

### Layout (approved via visual brainstorm)

Two-column, no page scroll needed on desktop:

- **Left (primary focus):** a full, realistic on-screen keyboard (all rows — function keys, number row, QWERTY block, modifiers) rendered as a CSS grid of key elements. The physically-pressed keys light up in real time as the user types. Below the keyboard, a text readout of the currently-detected combination (e.g. `ctrl + a`), taken directly from the library's own `getKeyCombination`/the entry the listener matched — not a separately-computed value, so the demo is provably using the real library output.
- **Right (sidebar):**
  - Two toggles: `keyMode` (`key` / `code`) and `checkInputElements` (on/off) — both wired to actually reconstruct the `BindKeyboard` instance with the new option live, so visitors can literally see layout-agnostic matching and input-guarding turn on and off.
  - A real `<input>` element, to test `checkInputElements` against.
  - A short static list of the demo's own registered bindings (see below), each flashing briefly when triggered.

### Registered demo bindings

A small set chosen to demonstrate real library features, not just decoration:

| Combination   | Type     | Options                                                                      | Demonstrates                                                                                                                                                                               |
| ------------- | -------- | ---------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `ctrl+a`      | keypress | `{ description: "Select all" }`                                              | basic binding                                                                                                                                                                              |
| `ctrl+z`      | keypress | `{ description: "Undo" }`                                                    | basic binding                                                                                                                                                                              |
| `escape`      | keydown  | `{ description: "Close the shortcuts overlay", allowInInputElements: true }` | fires even while the test `<input>` is focused and `checkInputElements` is on — visibly different from the other bindings, which get suppressed. No-op when the overlay is already closed. |
| `ctrl+/`      | keydown  | `{ description: "Toggle theme" }`                                            | punctuation combo (also exercises the `keyMode: "code"` punctuation fix from the earlier session)                                                                                          |
| `?` (shift+/) | keydown  | `{ description: "Show all shortcuts" }`                                      | opens the shortcuts overlay below                                                                                                                                                          |

### "Show all shortcuts" overlay

Pressing `?` opens a full-screen overlay listing **every currently-registered binding**, built by calling `bindKeyboard.getAllBindings()` and rendering each entry's `keyCombination` + `description` — this is a live demonstration of the exact pattern documented in the README's `.getAllBindings()` section. Closes via the same `escape` binding from the table above (a single binding serves both purposes: it's a no-op if the overlay isn't open) or a close button inside the overlay.

### Tech integration

- New `demo/` directory: `demo/index.html`, `demo/main.ts`, a small `demo/style.css`. `main.ts` imports `BindKeyboard` from `../src` directly (always in sync with the actual library code, not the published npm package).
- New `vite.demo.config.ts` — ordinary Vite app config (`root: "demo"`, normal build, **not** `build.lib`) so it doesn't interfere with the existing library-build `vite.config.ts`/`"build"` script at all.
- New `package.json` scripts: `"demo:dev": "vite --config vite.demo.config.ts"`, `"demo:build": "vite build --config vite.demo.config.ts"`.
- `.gitlab-ci.yml`: new `pages` job (stage `deploy`, runs on `main` only) that runs `npm run demo:build` and publishes the output as the `public/` artifact GitLab Pages expects.
- README: add a "Live demo" link/badge near the top.

### Visual style

Dark theme, monospace key labels, orange accent for "pressed"/active state — matching the mockups already approved during brainstorming. No separate design-system question needed; this is a single small page, not reused elsewhere.

## Out of scope (explicitly)

- Chord/sequence key bindings ("g then o") — noted as a known limitation, not built.
- A reusable "shortcuts panel" UI component shipped as part of the `bind-keyboard` package itself — the overlay is demo-page-only code, not a new library export.
- Blocking/throwing behavior for reserved shortcuts — hint-only, never blocks registration.
- Any browser other than GitLab Pages for hosting.

## Testing

- Stream 1: new unit tests per the coverage gaps listed, plus the new exports-smoke-check wired into CI.
- Stream 2: one new unit test (warn fires under `debug`, silent otherwise).
- Stream 3: no unit tests (it's a demo page, not part of the published package) — verified manually + a CI check that `npm run demo:build` succeeds, so a broken demo build fails the pipeline before it can reach Pages.
